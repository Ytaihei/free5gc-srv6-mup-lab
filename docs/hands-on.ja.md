# ハンズオン：登録、SRv6 MUP転送、ソース改変を確かめる

[English](hands-on.md) | 日本語

UEの登録からデータ通信、通常UPFへのフォールバック、小さなソース改変まで、自分の操作でラボを確認する手順です。まず演習1〜4を実施してください。復旧試験と改変は任意です。各演習に目的、期待結果、ダッシュボードの変化、復旧時の注意を記載します。

## 対象と安全上の注意

- **単一VMのコンパクト構成**、IPv4 UE 1台、サンプルのアドレス計画を対象とします。参照ドキュメントの6VM用 `make bootstrap` や `make test-one-call` は使いません。
- ホスト用コマンドは、KVMと動作するsystemdユーザーセッションを備えたUbuntu 24.04 x86-64上で実行します。MacはSSH・ブラウザーのクライアントとして利用でき、ネイティブなラボ実行ホストではありません。コンテナー内と記載したコマンドは、指定したコンテナーに入ってから実行します。
- ソースは公開済みですが、リリースイメージは配布していません。初回構築には `./lab up --build` を使います。既定VMは4 vCPU、8 GiB RAM、80 GiBの薄いディスクです。検証済み設定であり、最低要件を実証した値ではありません。ホスト側のメモリー・ディスクにも余裕を持たせ、依存取得のネットワーク接続を用意してください。
- 演習は1つずつ実行します。試験、起動、停止、多くの再ビルドはラボ通信を中断します。パケット証跡試験と同時に手動pingなどを実行しないでください。本番の加入者情報やネットワークは使用しません。
- 元のチェックアウト、非公開の `config/compact.local.yml`、`.lab/` 内の所有記録を一緒に保持してください。新しいcloneは既存VMを所有しません。衝突検査を回避するために、非公開状態をGitへ入れたり、所有記録を削除したり、他者のVMを流用したりしないでください。
- コマンドは既定の論理アドレスとダッシュボードのポート `8788` を使います。変更済みなら自身の値に読み替えてください。明示的なプロファイルでは、**すべての**サブコマンドの前に `./lab --config /absolute/profile.yml` を使います。CLI全体の既定値として保存されるわけではありません。

要件・設定は[単一VMセットアップ](compact-lab.ja.md)、用語は[用語集](glossary.ja.md)、制御・転送の役割は[アーキテクチャ](architecture.ja.md)を参照してください。CLIのID `tpe` と `npe` は、それぞれMUP PE（N3／Interwork側）とMUP PE（N6／Direct側）です。仕様で定義された用語ではありません。

## 準備：既存ラボか新規構築かを選ぶ

**既存のコンパクトラボ**では、作成に使用したチェックアウトとプロファイルを使います。cloneと初回構築は省略してください。所有するVMが停止中なら `./lab up` を実行し、稼働中なら演習1へ進みます。起動はUEを再接続し、カーネル変更後などにはダウンロードが必要な場合があります。

**準備済みで衝突のないホスト上に新規構築**する場合は、公開ソースをcloneします。

```bash
git clone https://github.com/Ytaihei/free5gc-srv6-mup-lab.git
cd free5gc-srv6-mup-lab
./lab deps
sudo ./lab deps --apply
```

最初の依存コマンドは変更のプレビュー、2つ目はホストのパッケージ・グループ変更の適用です。グループ所属が変わった場合はログアウト・再ログインし、このディレクトリに戻ってから実行します。

```bash
./lab doctor
./lab up --build
```

期待結果は、`doctor` の `PASS`、ソースビルドの完了、起動時の実UE登録・データ疎通の成功表示です。失敗した場合は先へ進まないでください。名前、アドレス、ストレージ、ポート `8788` が衝突する場合は停止し、セットアップ手順に従ってVM作成**前**に別プロファイルを用意してください。既定値を使うために既存ラボを削除してはいけません。配布リリースがない間、新しいcloneで単に `./lab up` を実行すると意図的に停止します。

**ラボホスト上**のブラウザーで `http://127.0.0.1:8788/` を開きます。リモート端末では、このアドレスはホストではなく端末自身を指します。設定済みのTailnetを利用する場合は、ラボホストで明示的にTailnet専用の待ち受けを追加します。

```bash
./lab dashboard start --tailnet
```

表示されたURLを、接続が許可されたTailnet端末から開いてください。ダッシュボードは設定を変更しませんが、到達可能な利用者にラボ・セッション情報を返し、アプリケーションのログイン機能はありません。インターネットへ直接公開しないでください。追加の待ち受けを解除するには `./lab dashboard start --local` を使います。通常 `8787` を使う6VM版ダッシュボードは、別のラボです。

## 演習1：準備状態を確認する

**目的：** コンテナーが起動していることと、制御・転送プレーンが利用可能なことを区別します。

ホストで実行します。

```bash
./lab status
./lab health
```

| 確認項目 | 既定の1 UEでの期待結果 |
| --- | --- |
| コンテナー | 構成されたサービスが稼働中 |
| Observerリース | `observer_lease_valid` が `true` |
| BGP接続 | `bgp_state` が `2/2 established` |
| PFCPセッション | `observed_sessions` と `selected_sessions` がともに1 |
| MUPセッション経路 | `advertised_routes` が2：下りT1と上りT2 |
| healthコマンド | `PASS` とともに正常終了 |

**画面：** 新鮮なスナップショット、有効なリース、BGP接続2件、セッション1件、セッション経路2件、UE→DNのprobe成功を確認します。`health` は両PEのAPIを検査し、UEからpingも送ります。ダッシュボードの `/healthz` はスナップショットの鮮度だけを確認するため、そこでのHTTP 204はラボ全体の正常性を証明しません。

**復旧：** 失敗した場合は通信に影響する試験へ進まず、後述のトラブルシューティングで診断します。古い緑色の画面を合格と扱わないでください。

## 演習2：UEから自分で通信する

**目的：** 管理インターフェースではなく、UEのトンネルから通信できることを確認します。ホストからUEコンテナーに入ります。

```bash
./lab shell ue
```

**UEコンテナー内**で実行し、最後に退出します。

```bash
ip address show uesimtun0
ping -I uesimtun0 -c 5 10.210.6.15
curl --interface uesimtun0 --max-time 10 http://10.210.6.15/
exit
```

**期待結果：** トンネルにUEアドレスがあり、ping 5回すべてに応答し、HTTP本文に `free5GC SRv6 MUP lab data network` が含まれます。登録後にUEアドレスが変わることがあるため、以前のUEアドレスを固定値として使わないでください。

**画面：** MUP経路が有効なら、定期probeの成功とPEカウンターの増加を確認できます。アニメーションは収集状態とprobeからの推定であり、個々のパケットの追跡ではありません。ping成功だけではMUPによる迂回を証明しないため、演習3・4でパケットを確認します。

**復旧：** `exit` でホストへ戻ります。トンネルがない場合や通信に失敗した場合は原因を調べ、インターフェース指定を外して成功扱いにしないでください。自動試験の前に手動通信を終了します。

## 演習3：登録からデータ疎通までの1callを実行する

**目的：** 合成セッションではなく、実際のシグナリングと転送を試します。画面を開いたまま、ホストで実行します。

```bash
./lab test one-call
```

UEの登録を解除し、PFCPの削除とT1/T2撤回を待ち、再登録、新しいPDUセッション、PFCP由来のMUP広告を待ちます。登録・PDU成功ログ、ICMP 8往復、期待するHTTP本文、両PEのredirectカウンター、相関するパケットとPEごとのBPF証跡を要求します。MUP通信では、検査対象のUEパケットがUPFのN3/N6インターフェースに現れないことも確認します。

**期待結果：** 正常終了、制御・パケット証跡の表示、および次のメッセージです。

```text
PASS: one-call Registration -> PDU -> PFCP -> MUP -> ICMP/HTTP
```

**画面：** セッション・経路が消えて復元され、最後はセッション1件、経路2件になります。5秒ごとの更新では短い変化を見逃すことがあります。コンパクト試験には6VMスクリプトの `OBSERVE_SECONDS` による待機機能はありません。パケット検査中は証跡への混入を避けるため定期probeを休止し、この間の `idle` は測定したパケット障害ではありません。読み取り専用の状態収集は継続します。

**復旧：** 登録解除で失敗してもUEの起動を試みますが、無条件に復旧を保証するものではありません。エラー・中断後はログを確認し、`./lab health` を実行してから次へ進みます。成功時はUE登録とMUP有効状態を残します。ここでいうcallは登録とデータセッションであり、音声通話ではありません。

## 演習4：MUPと通常UPFへのフォールバックを比較する

**目的：** MUP経路を撤回しても、基礎となるPFCPセッションを削除する必要がないことを確認します。ホストで実行します。

```bash
./lab test baseline
```

| 段階 | MUPセッション経路 | 期待するユーザーパス |
| --- | ---: | --- |
| 最初の選択状態 | 2 | SRv6 MUP |
| セッションの広告を抑止 | 0 | 同じPFCPセッションを使う通常UPF |
| 抑止を解除 | 2 | 再びSRv6 MUP |

フォールバック中は、同じICMPパケットがUPFの両インターフェースにあり、SRv6ブリッジにはないことを確認します。その後、MUP経路も再検証します。現在の `./lab test mup` は同じシナリオを呼び出すため、両方を実行する必要はありません。

**期待結果：** 正常終了と次のメッセージです。

```text
PASS: ordinary UPF fallback and MUP resume for the same PFCP session
```

**画面：** PFCPセッションを維持したまま経路数が変わり、パスが切り替わります。短いフォールバック期間は更新間隔により見逃す場合があります。試験パケットが通った経路は、アニメーションだけではなく自動取得したパケット証跡で確認します。

**復旧：** 失敗時も抑止したセッションの再開を試みます。その後に `./lab health` を確認し、経路が撤回されたままなら後述の診断を行ってください。フォールバックには、正常なUPFセッションと経路が必要です。

## 演習5：障害復旧を試す（任意）

**目的：** 特定の管理された障害・復旧ケースを確認します。ラボ通信を中断するため、ホストで1つずつ選んで実行します。

| コマンド | 意図する変更と期待結果 |
| --- | --- |
| `./lab test lease` | Observerを停止し、15秒のリース失効とMUP撤回を待ち、UPFへのフォールバックを確認してから観測を再開し、実UEを再登録 |
| `./lab test restart` | イメージ・コンテナーIDを変えず両PEコンテナーを再起動し、管理された初期設定を適用して、新しいcallの前に既存セッションを検査 |
| `./lab test network` | 両PEコンテナーとネットワーク名前空間だけを再作成し、経路・VRF所属を復元して転送を確認 |
| `./lab test neighbor` | N6／Direct側PEのDN向け動的近隣エントリーだけを削除し、定期処理による30秒以内の復元を要求 |

**期待結果：** 選択したコマンドが正常終了し、その後の `./lab health` に合格することです。画面ではシナリオに応じて、経路撤回、peer停止、probeの休止・失敗が一時的に現れ、復旧します。既存のシグナリングを見逃したObserverは、再起動だけではそのセッションを再構成できません。lease試験は意図的に新しいUE/PFCPシグナリングを生成します。

**復旧：** 失敗時は診断と証跡を保存し、トラブルシューティングへ進みます。範囲を限定した管理下の復旧試験であり、任意のクラッシュから無操作・無損失で復旧する保証ではありません。

個別に選ぶ代わりに、すべてのパケット・復旧シナリオを実行する場合：

```bash
./lab test all
./lab health
```

演習3・4と上記4シナリオを含みます。クリーン構築、VM再起動、別物理ホストの試験、性能測定ではありません。

## 演習6：ダッシュボードを改変して戻す（任意）

**目的：** パケット処理を変更する前に、ソース編集、部品の再ビルド、イメージのrollbackを確認します。ホストで実行します。

```bash
./lab source mup-dashboard
```

表示されたソースディレクトリで、エディターを使い `internal/dashboard/web/index.html` の表示見出しだけを変更します。

```html
<h1>SRv6 MUP Observatory</h1>
```

例えば次のようにします。

```html
<h1>My SRv6 MUP Lab</h1>
```

既存の編集内容を把握し、上書きしないでください。その後、ホストのチェックアウトで実行します。

```bash
./lab rebuild mup-dashboard
./lab builds
./lab health
```

**期待結果：** ビルドが成功し、その記録がactiveになり、ブラウザー再読み込みで見出しが変わることです。ダッシュボード・コレクターの再起動により表示更新が一時的に中断する場合があります。必要ならキャッシュを使わない再読み込みを行ってください。

**復旧とrollback：** 再ビルド成功を確認してから、以前のダッシュボードイメージへ戻します。

```bash
./lab rollback mup-dashboard
./lab health
```

ブラウザーを再読み込みすると、前の見出しに戻ります。rollbackが戻すのは以前のイメージであり、**ホスト上のソースファイルやDBではありません**。ソースも元に戻したい場合は、エディターで自分の見出し変更だけを戻してください。戻さなければ、次の再ビルドで改変した見出しが再び反映されます。無関係の編集を破棄したり、rollbackに必要なイメージをpruneしたりしないでください。コンパイル失敗では新イメージを有効化しません。有効化後の失敗は復旧を試み、未完了トランザクションがあれば報告します。制限は[開発操作](prebuilt-development.ja.md)を参照してください。

## 結果を確認し、終了する

ホストで実行します。

```bash
./lab evidence
./lab logs ue
./lab logs observer
./lab logs mupc
```

evidenceコマンドは、記録された場合には失敗した復旧結果も含め、保存済み結果の概要を一覧します。試験の再実行や承認ではありません。過去の成功ではなく、最新実行、その結果、試験の終了状態を確認してください。生PCAP、BPFダンプ、結果は**ゲスト内**の `/opt/srv6-mup-compact/.lab/runtime/evidence/` にあります。失敗によってはキャプチャー・ログがあっても完了結果の概要がない場合があるため、診断用に保持します。新規キャプチャー、ログ、スナップショット、診断結果は既定で非公開とし、別途レビューせずGitHubへアップロードしないでください。配布用の例示は[レビュー済みPCAPの解説](../examples/pcap/one-call/README.ja.md)を参照してください。

実験を続ける場合は稼働したままにし、終了する場合は所有するコンパクトVMを停止します。

```bash
./lab down
```

ダッシュボードのトンネルを停止し、VMを通常終了させます。ディスク、ソース、記録は保持します。後日、同じチェックアウト・プロファイルから再開します。

```bash
./lab up
./lab health
```

起動時はUEを再接続し、無停止の一時停止・再開ではありません。通常終了に `destroy` を使わず、`.lab/` も削除しないでください。既存VMの再利用は、新たにcloneした公開リビジョンのクリーン再現ではありません。

## トラブルシューティングと合格条件

コマンドが失敗したら演習を止め、範囲を限定した診断を取得します。

```bash
./lab diagnose
./lab dashboard status
```

| 症状 | 次の確認・対応 |
| --- | --- |
| 初回の通常起動でリリースがないと表示 | 意図した新規ソースビルドのラボに限り `./lab up --build` を使用 |
| KVM・グループ・メモリー・ストレージ・ネットワーク検査が失敗 | 指摘された前提条件を解消し、グループ変更後は再ログイン。所有・衝突検査は迂回しない |
| 新しいcloneが既存VMを拒否 | 元の所有チェックアウト・プロファイルへ戻るか、衝突しない別VMを設定 |
| ブラウザーが接続できない | ホストと端末のループバック、設定ポート、VM・トンネル状態、Tailnetアクセスを確認。公開用のワイルドカード待ち受けを開かない |
| パケット試験中にprobeが `idle` | 証跡への干渉回避なので試験終了を待つ。ping成功でも、観測した損失でもない |
| スナップショットが古い、または `/healthz` が503 | コレクター・トンネル状態を確認し、古いトポロジーを現在値として扱わない |
| 中断した試験の後、経路が撤回されたまま | `./lab logs mupc`、Observer・UEログと診断を確認。証跡を保持した後の `./lab up` は通信を中断して協調再起動・再接続し、未完了の有効化の復旧も試みる |
| rebuild・rollbackの復旧が未完了 | 状態とイメージを保持し、トランザクション記録を削除せず開発手順を参照 |

復旧を試みた後は `./lab health` を実行します。ラボが正常に戻っただけで失敗した演習を合格にせず、安全に実施できる時点でその演習を再実行してください。基本の受け入れ条件は、演習1〜4と終了後のhealthへの合格です。改変を確認する場合は、見出し変更とイメージrollbackの表示も確認します。この手順は実装に照らした確認方法であり、文書の追加・翻訳自体が新たな実機実行、広い標準準拠、別ホスト再現の証拠になるわけではありません。

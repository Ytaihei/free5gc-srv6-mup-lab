# リポジトリ公開チェックリスト

[English](publication-checklist.md) | 日本語

レビュー済みの公開ソース候補と、公開が承認されたGitHubリポジトリは別です。ソース・依存関係・秘密情報の検査成功は、全面的な脆弱性監査、法的認証、稼働ラボの外部公開許可ではありません。

## 復旧用の履歴は非公開で保持する

- 既存の復旧用リポジトリは非公開で残します。私用ファイル、ブランチ、作成者メタデータ、過去コミットは公開製品の一部ではありません。
- 統合済みブランチを削除してもデフォルトブランチの履歴は消えません。その履歴から別ブランチを作るだけではクリーンなリリースになりません。
- レビュー済みの履歴なしソース書き出しから別リポジトリを開始します。fork・mirror、旧 `.git` のコピー、旧refsの持ち込みはしません。公開に `git push --all` や `git push --mirror` を使わないでください。
- 復旧側の統合済みブランチは、固有コミットとPRを確認した上で整理目的で削除できます。削除は別途明示的に行う操作で、ソース書き出しの前提でも秘匿化の保証でもありません。

[GitHubの公開設定の説明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)では、公開によりActions履歴・ログも見えるようになるとされています。[機微情報削除の説明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)も、PR参照やキャッシュが残ることを説明しています。ブランチ整理だけではこれらを秘匿化できません。

## ソースと成果物の確認

- 対象コミットを固定し、`config/public-source.json` の対象だけを書き出します。[ソース配布手順](source-distribution.ja.md)に従い、外部の非公開識別情報リスト、Gitleaks、展開ツリー検査を実行します。内容に加えてパスも調べます。
- 正式なLICENSE、上流への帰属表示、第三者通知を保持します。公開サンプルのアドレスやUE認証情報は意図したラボ用fixtureで、本番用ではありません。所有者・moduleの帰属表示は意図したもので、秘密情報として一律に削除しないでください。
- ローカル設定、SSH関連情報、加入者DB、未レビューのPCAP、スクリーンショット、生のダッシュボードJSON、非公開ログ、VM・コンテナー・バイナリの書き出しをGitに入れません。ラボ内だけの例示PCAPにも識別子、認証交換、時刻、仮想MACが残るため、成果物ごとに別途レビュー・承認します。`config/public-pcaps.json` とソース一覧で固定した[レビュー済み例示](../examples/pcap/one-call/README.ja.md)のみGit管理・配布の例外です。バイト列・ハッシュの変更にはパケット単位の再レビューが必要です。
- 日英両方の文書、リンク先、画像メタデータ、ファイル名、author/committer/taggerの識別情報を確認します。ハッシュは翻訳品質を証明せず、未知・符号化された秘匿情報をすべて検出するものでもありません。
- 新規公開ソースリポジトリでは、現在のファイルだけでなく `--check-history` で利用可能な全ローカルrefsを調べます。完全なcloneを使い、リモートのブランチ・タグ・PR refsとも別途照合します。このツール自身はrefsを取得しません。
- 候補のダイジェストと検査結果は、そのリリース記録自体をレビューするまで非公開で保持します。非公開監査報告を公開ツリーにコピーしないでください。

## 公開先とGitHub設定の確認

- 公開操作前に公開先owner/nameと候補のダイジェストを承認します。名前が変わる場合はGo module/importパス、Issueフォームのリンク、CODEOWNERS、文書、CI、報告先を合わせ、再検査します。
- 公開側の統合先は `main` とし、短期の機能・文書ブランチ、PR、成功したCIを使います。`test`、`gitleaks`、`source-and-binaries` を必須検査にし、統合ブランチの削除・force-pushを禁止し、実際の保守体制に適したレビュー要件を設定します。公開設定変更後も有効性を確認します。公開側の統合済み作業ブランチは自動削除を推奨し、レビュー済みリリースタグは保持します。
- 脆弱性を非公開で報告できる窓口の動作を確認します。IssueフォームのURLがあるだけでは有効とは限りません。GitHub標準機能は公開リポジトリ向けで、非公開repoでの404から将来の状態は判断できません。[GitHubの報告機能の設定](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository)を確認してください。
- リポジトリの説明・ホームページ、Issue/PR本文とコメント、Wiki、Discussions、Pages、deployments、Actionsログ・成果物・キャッシュ、リリースと添付をレビューします。復旧repoの既存記録は移しません。使わない公開面は無効にするか、レビュー済み情報だけで構成します。
- Actionsの権限を最小限にし、checkout後に認証情報を残さず、成果物の保持期間を制限します。実際の非公開識別情報を公開CI変数、報告、画面画像、テストfixtureへ入れないでください。
- 公開後はラボ本体を公開repoで開発し、マシン固有の運用と非公開の証拠は分離します。同期のために復旧履歴をマージしないでください。

## 最終判断の記録

所有者が公開先、正確なソースダイジェスト、確認済みの作成者・報告先、ソース・ライセンス・プライバシー検査、リモートrefsとメタデータの確認、CI・ルールの検証、最終的な明示的承認を記録するまで公開はpendingです。確認できなかった項目を合格にせず、未確認と記録します。稼働サービスの公開、バイナリ・イメージ・PCAPの配布には、それぞれの範囲と承認が必要です。

## 判断の引き継ぎ：2026-09-28（日本時間）

| 成果物 | 技術的な判定 | 残る条件 |
| --- | --- | --- |
| 履歴なしソース書き出し | 最終展開ツリー検査後、ソースのみの公開候補 | 所有者・公開先、作成者・窓口の確認、正確なdigestと明示的承認、新repoの設定・CI検証 |
| ランタイム・NFイメージ | 最新一式のHIGH／CRITICAL候補が0でも未承認 | 対応ソース・ライセンス、一部の鍵パターンの由来、リリース経路の試験、公開時の制御 |
| 任意のビルダーと上流DB | 再配布はNO-GO | 脆弱性候補の確認・修正と別途の配布条件。DBは上流からの直接取得を維持 |
| 稼働ラボ・非公開証跡・復旧履歴 | 公開ソース候補の対象外 | 別途の明示的承認。非公開を維持 |

完了したオフラインのソースレビューは、固定した書き出し候補の全241ファイルを対象にしました。6 VMの試験スクリプトで、コントローラーのセッション識別子をSSHのシェル文字列へ展開するコマンド注入経路を1件確認しました。深刻度はmedium、確信度はhighで、管理ネットワークへの到達と、後から管理者が試験を実行することが前提です。最終ソースでは後処理を含む全6箇所のsuppress／resumeを共通の引数エンコード処理へ置き換え、特殊文字の往復と呼び出し箇所の回帰テストを追加しました。固定対象のレビューには指摘を残し、修正と試験証跡を分けています。過去の監査を指摘0件へ書き換えず、稼働ラボへの攻撃試験も行っていません。

隔離したコンパクト候補では、全パケット・復旧試験と単体rebuild／1call／rollbackが成功しました。主ラボは稼働を維持し、候補VMは状態を残して停止しました。別物理ホストでの試験は明示的な範囲指定により未実施です。上流依存の完全な実装、稼働環境の安全性、非公開の復旧履歴はオフラインのソースレビュー対象外です。成果物に結び付いた件数と、条件付きの構築済みダッシュボードのソケットアクセス不具合を含む未解決条件は、[イメージ配布](image-distribution.ja.md)を参照してください。既定の`release: null`での初回`./lab up`は配布済みイメージによる導入経路ではなく、現時点ではソースビルドが利用可能な経路です。

最終書き出しのハッシュ、ソースrevision、成功したCIのrun ID、監査報告、修正確認ログ、例外事項は非公開の判断記録に保持します。最終梱包検査は、以前の固定監査アーカイブではなく、修正を確定したバイト列に結び付けてください。架空のテスト用作成者で初期化したローカルの1コミットrepoでは梱包・履歴検査を確認できますが、実際の作成者や公開先を承認したことにはなりません。このチェックリスト自体はrepo・イメージの公開や可視性変更を許可しません。

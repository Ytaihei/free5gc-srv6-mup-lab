# 単一VMラボへの移行

[English](compact-lab.md) | 日本語

## 現在の状態と配布の境界

これは**実装途中の実験用構成**であり、新しい標準構成や公開済みアプライアンスではありません。既存の6 VM構成は変更しません。ランタイムイメージも新規リポジトリも公開していません。初回作成には`./lab up --build`が必要です。作成後は`./lab up`でVM内のローカル候補イメージを再利用し、アプリケーションの再ビルドなしで再開できます。レビュー済み配布イメージが存在するという意味ではありません。

目標は、Ubuntu x86-64のKVM VMを1台だけ作り、その中にComposeで5G/MUPラボを構築することです。ビルド済みイメージで起動し、部品単位でソースをカスタマイズできるようにします。最初の互換性確認ではUbuntu 24.04、Linux 6.8、固定版gtp5g、veth上のVinbero generic XDPを使います。既存のvirtio driver-mode XDPとの性能同等性は主張しません。PFCP、BGP MUP、ユーザーパケットは実際に流し、合成セッションの注入で置き換えません。

## ローカルM1候補の実行

[構築済みイメージ／開発の操作](prebuilt-development.ja.md)では、実装済みのdigest固定リリース読込み、必要時のみのビルダー取得、CIの範囲を説明しています。配布承認までは同梱のリリース定義を空に保ちます。

前提はUbuntu 24.04 x86-64、libvirt/KVM、Python YAML/Jinja2、OpenSSH、curl、Git、qemu-img、virt-install、動作するsystemdユーザーセッションです。`./lab deps`はPythonモジュールが未導入でもパッケージ・グループ変更の計画を表示します。`sudo ./lab deps --apply`で明示的に導入し、既定のイメージディレクトリがなければ作成します。グループ変更後はログアウト・ログインしてください。既存ディレクトリの権限は保持するため、独自のイメージディレクトリは事前に作成し、書き込める必要があります。ホストにDockerやGoは導入せず、既存ラボも設定しません。日本時間2026-09-20に、nested KVMを使える新規Ubuntu親VMへの依存導入と、再接続後のグループ反映を検証しました。別の物理ホストでの検証ではありません。

新しくダウンロードしてchecksum検証したクラウドイメージは、利用者が`umask 077`を使っていてもグループ`kvm`・権限`0640`にします。libvirtが所有者を変更しても、この公開ベースイメージを読み取れるようにするためです。既存キャッシュは検証しますが、権限は自動変更しません。旧キャッシュを読み取れない場合は、所有者がそのイメージに限って利用者の`kvm`グループへ読み取りを許可してください。共有イメージディレクトリ全体の権限を再帰的に変更しないでください。

```bash
./lab deps
sudo ./lab deps --apply
./lab doctor
./lab up --build
./lab status
./lab health
./lab test one-call
./lab test baseline
./lab test lease
./lab test restart
./lab test network
./lab test neighbor
./lab test all
./lab evidence
./lab logs tpe
./lab shell tpe
./lab diagnose
./lab dashboard status
./lab destroy
./lab down
./lab up
```

`up --build`は、**新しく作ったVM内での**ソースビルドを明示的に選択します。既存ラボのゲスト、物理ホストのDocker、物理ホストのカーネルモジュールは変更しません。共通ランタイムのアプリケーションも、固定ツールチェーンと保存済みソースを使う分離ビルダーで構築します。free5GCの全11 NF／WebUIも、固定ソースから分離したM3ビルダーとクリーンなUbuntuランタイムベースを使って自動構築します。その後の部品単位の`rebuild`も同じビルダーを使います。公開済みランタイム／ビルダーイメージは不要です。

`up`はUEを再接続し、依存順にcore/observerを再起動します。無停止操作ではありません。設定ファイルのハッシュが変わればコンテナーを再作成します。ライフサイクル・試験操作にはホストとゲストのロックがあります。カーネル変更時はgtp5gのクリーンビルド、vermagicの厳密な一致確認、協調したモジュール再ロードを行うため、アプリケーションイメージがキャッシュ済みでもネットワークアクセスが必要な場合があります。加入者設定更新時には認証シーケンス番号を保持します。

任意の設定変更はGit管理対象外の`config/compact.local.yml`、または`./lab --config /absolute/profile.yml ...`で指定します。`config/compact.example.yml`への部分的な上書きです。論理設定の`networks`、`subscriber`、`mup`はレビュー済み`lab.example.yml`を継承し、既存環境のローカル設定は読みません。`dashboard_port`の既定値は物理ホストのループバック上の8788で、ほかのサービスが使用していない必要があります。

既定VMは4 vCPU、8 GiB RAM、80 GiBの薄いディスクと独立したNAT管理ネットワークを持ちます。利用可能メモリー、空き容量、経路・ネットワークの重複、所有記録をチェックします。この割り当ては検証目標であり、**最低動作要件として実証した値ではありません**。既存VMの流用はせず、衝突した場合は停止します。サンプルのサブネットが使用済みなら、初回作成前にローカル設定で未使用サブネットと対応するgateway/addressを指定してください。作成後のVM設定は固定し、設定変更で既存状態を自動移行しません。

`.lab/<vm-name>/`には専用SSH鍵、known_hosts、転送用ソースアーカイブ、UUID所有記録を保存します。これらは非公開とし、VMが存在する間は所有記録を保持してください。`down`はダッシュボードのトンネルを停止し、VMの通常終了を待ち、ディスクとソースを保持します。VMの自動起動は設定しません。

`./lab destroy`はプレビューだけです。適用には`./lab destroy --confirm srv6-mup-compact`のように設定と一致するVM名を明示します。所有記録の不一致、追加ディスク、シンボリックリンク、別ドメインによるネットワーク／ディスク利用があれば拒否します。対象を通常停止し、所有するlibvirt定義だけを削除します。ディスクは元の場所でUUID付きの`*-retired-*.qcow2`へ改名し、非公開状態は`.lab/retired/<UUID>/`へ移します。ディスク、ソース、pcap、ベースイメージは削除しません。退避先も非公開に保ってください。手動復旧には保存した定義・所有記録と元のパスへの復元が必要で、新規`up`では復旧しません。退避処理は単体試験に加え、後述の日付付き記録にある使い捨て検証VMでも確認しました。主ラボは廃止していません。

## ランタイムの分離

Composeの7つのブリッジで、管理、SBI/N4、N2、N3 access、N3 core、SRv6、N6を分離します。いずれもinternalネットワークで、masqueradeを無効にします。N4 observerだけは**ゲストOSの**ネットワーク名前空間を使い、UID 0で`CAP_NET_RAW`以外の権限を落として`br-free5gc`をキャプチャーします。検証したDockerでは非root UIDでキャプチャー権限が有効にならなかったためです。物理ホストのネットワークではなく、Dockerソケットも渡しません。UEはgNBの名前空間を共有しますが、別コンテナーとして停止・起動できます。PEには必要なネットワーク/BPF権限を与え、無制限のprivilegedコンテナーにはしません。DNのHTTPは試験用応答だけを配信し、加入者設定を公開しません。

PEのAPIと初期設定、BGP接続、observerのリースを確認してからgNBとUEを起動します。失敗は報告し、VMを診断用に保持します。既存のPFCPトランザクション受理条件とリースの意味は変えません。N6の送信元NATなしで、通常UPF経由の経路も残します。

generic XDPの機能検証用設定では、DN/RANのデータインターフェースとPEで送信チェックサム・セグメンテーションのオフロードを無効にします。最初のDN設定ではpingは通ってもHTTPが失敗しました。修正後は実TCP通信とN3内側パケットのチェックサムを検証しています。baseline試験がN6の意図した次ホップを変えてしまわないようICMP redirectも無効にします。インターフェース単位の設定にはDockerの[endpoint sysctl機構](https://docs.docker.com/reference/cli/docker/network/connect/#set-sysctls-for-a-containers-interface---driver-opt)を使います。NRFが生成する証明書は固定した上流ソースツリーではなく非公開のランタイム領域に置き、NRFだけに書き込みを許可します。

## ダッシュボードと診断

表示名は **MUP PE（N3／Interwork側）** と **MUP PE（N6／Direct側）** に統一します。英語ではMUP PE (N3/Interwork side)、MUP PE (N6/Direct side)と表記し、`tpe`／`npe` は内部識別名としてのみ補記します。Composeサービス名、JSONのノード／PE ID、設定キー、`./lab logs tpe` や `./lab shell tpe` などの操作は変更しません。APIの人が読むPE名・役割は英語表記に更新するため、外部の処理は表示名でなく固定IDで照合してください。[用語集](glossary.ja.md)も参照してください。

`up`はゲスト内のsystemdコレクターとComposeのWebコンテナーを起動し、監視付きユーザーサービスのSSHトンネルを開始します。物理ホストで`http://127.0.0.1:8788/`を開いてください。既定では外部へ公開しません。公開範囲は明示的に選びます。

```bash
./lab dashboard start --tailnet
./lab dashboard start --local
./lab dashboard stop
./lab dashboard start
./lab dashboard status
./lab diagnose
```

`--tailnet`はホストのTailscale IPv4アドレスだけに待ち受けを追加します。ワイルドカード、Tailscale Serve、Funnelは使いません。最後に成功した公開範囲を次回`up`でも保持し、`--local`で追加の待ち受けを解除します。Tailscaleの導入・ログインとTailnetのACL管理は利用者が行います。APIは読み取り専用ですが、ポートへ到達できる相手には認証なしでラボのアドレスやセッション情報を返すため、インターネットへ直接公開しないでください。

コレクターは**専用VM内だけ**で特権動作し、固定したDockerの状態取得・exec操作と5秒ごとのUE pingを行います。HTTPやコマンドを受ける待ち受けは持ちません。原子的に更新するスナップショットをWebコンテナーへ読み取り専用で渡します。WebプロセスはUID 65534で、capabilityなし、ルートファイルシステム読み取り専用、`network_mode: none`です。Dockerソケット、SSH鍵、加入者設定は持ちません。別の書き込み可能ディレクトリにUnix HTTPソケットを置き、SSHで転送するため、ゲストのTCPポートは公開しません。ゲスト内のローカルユーザーはそのUnixソケットで同じAPIを読めます。

30秒より古いスナップショット、欠落・不正なファイル、5秒を超える未来の時刻は`stale`／`offline`にし、有効経路・probe成功の表示を解除し、`/healthz`がHTTP 503を返します。新鮮ならラボ自体がdegradedでも204を返します。このエンドポイントは収集の鮮度を示し、`./lab health`は実際のネットワーク準備状態も調べます。パケット証跡試験中は共有ロックで定期probeだけを休止し、読み取り専用収集は続けます。休止中は成功扱いにせずidleを表示します。5秒ポーリングでは短時間の登録・withdrawal遷移を見逃す場合があるため、完全なイベント列の証跡にはpcapやログを使ってください。

`diagnose`は生ログ、環境変数、認証設定を含めず、ホスト・ゲストのバージョン、所有情報、サービスとネットワーク状態を取得します。能動probeは送りません。省略したprobeはidle／degradedであり、通信失敗を測定した意味ではありません。出力にはローカルパス、UUID、ラボアドレスが残るため、そのまま公開用に無害化された資料ではありません。SSHトンネルはユーザーマネージャー稼働中に障害から再起動しますが、ホスト起動時の自動起動や最終ユーザーのログアウト後の継続までは保証しません。既存6VM版ダッシュボードは別のままで変更しません。

## 部品単位の開発

実験用の`source`、`rebuild`、`rollback`、`builds`コマンドを追加しました。対象は`mup-controller`、`pfcp-observer`、`mupctl`、`mup-dashboard`、`vinbero`、`ueransim`と、`free5gc-amf`、`free5gc-ausf`、`free5gc-chf`、`free5gc-nrf`、`free5gc-nssf`、`free5gc-pcf`、`free5gc-smf`、`free5gc-udm`、`free5gc-udr`、`free5gc-upf`、`free5gc-webui`です。MongoDBは意図的に再ビルド対象に含めません。

```bash
./lab source vinbero
./lab source free5gc-smf
./lab rebuild vinbero
./lab rebuild free5gc-smf
./lab builds
./lab rollback free5gc-smf
./lab health
```

`source`は編集できる**物理ホスト上の**ディレクトリを表示します。独自Goツールはこのリポジトリ、外部部品はGit管理対象外の`worktrees/<component>/`を使用し、固定コミットで初期化します。Vinberoには初期化時に一度だけレビュー済みMUPパッチを適用します。既存ツリーのreset・clean・上書きは行わず、ローカルコミットと未コミットの編集を保持します。所有記録は`.lab/source-records/`に保存します。初回fetchの途中失敗やソースlockの変更時は、現時点では自動削除せず利用者による診断が必要です。free5GC各NF／WebUIのコミットは固定した[free5GC v4.2.3ツリー](https://github.com/free5gc/free5gc/tree/3b34a08e93a9b334f0f4005d3a3a9f79b66d59b9)のgitlinkであり、変更可能なイメージタグから推測しません。

`rebuild`はハッシュ付きソーススナップショットを所有VMへ転送し、非rootビルダーでビルドします。ルートファイルシステムとソースマウントは読み取り専用、capabilityなし、Dockerソケット・SSH鍵・設定のマウントなしで、メモリー3 GiB・CPU 2個に制限します。ビルダーはネットワーク経由でビルド依存を取得できます。Go・Node・Yarnの配布物とベースイメージはchecksum／digestを固定し、ローカルで作ったビルダーは不変のイメージIDで再利用してパッケージの版も記録します。aptリポジトリはスナップショット固定していないため、別の日にビルダーを作り直して同じバイト列になる保証はありません。

Gitメタデータ、ローカル設定、鍵、生pcap、ビルドディレクトリ、依存キャッシュは転送から除外します。独自Goのスナップショットには`go.mod`、`go.sum`、`api`、`cmd`、`internal`の新規ソースも含めます。外部部品は追跡済みファイルとignoreされていない新規ファイルを対象にし、シンボリックリンクは辿らず拒否します。カスタムソースは対応する場所へ置いてください。入力ファイルと実行モードのハッシュに加え、ビルド記録には解決後のモジュールlock、ビルダー／イメージID、成果物ハッシュも保持します。スナップショット、作業領域、キャッシュ、失敗成果物はホスト／ゲストの`.lab/`内に非公開で保持し、自動削除しません。

履歴を含まないソース配布にも対応します。ソースディレクトリにGitメタデータがなければ任意のコミット欄をnullとし、ファイルとモードのハッシュでスナップショットを識別します。外部ソースの作業ツリーには引き続きGitが必要です。

コンパイル失敗では選択中・稼働中のイメージを変更しません。成功後は対象サービスの既存ランタイムに候補レイヤーを追加し、不変のイメージIDで切り替えます。ダッシュボード変更はWebコンテナー／コレクターだけを再起動して鮮度を検証します。それ以外は慎重な`up`再接続順序と実MUPパケット・ICMP・HTTP試験を使うため、イメージ置換は部品単位でも、**無停止でも対象部品だけの再起動でもありません**。独自Goは全Go試験、VinberoはMUP試験とeBPF再生成、free5GCはテスト本体を実行しないコンパイル確認後に実ラボ試験を行います。WebUIは不変のYarn lockでフロントエンドも構築します。上流の全適合性試験を実施した意味ではありません。

切り替え後の検証に失敗すると以前のイメージを選び、復旧を検証します。復旧も失敗した場合は未完了トランザクションを保持して失敗を報告し、次の`up`で以前の選択へ戻してから再試行します。`rollback`が戻すのは直前の成功イメージであり、ソースツリーやDB内容ではありません。同じサービスを共有する`mup-controller`と`mupctl`は変更の逆順で戻す必要があり、競合すれば拒否します。DB／設定スキーマの移行はこのイメージロールバックの対象外です。復旧に必要な保存イメージIDをpruneしないでください。独自イメージ選択は`up --build`を含む`up`で保持し、初回構築用の候補を作り直しても無断で上書きしません。

`builds`の`active`は、そのビルドのイメージIDそのものが対象サービスすべてに選択されていることを示します。後からmupctlのレイヤーを追加すると、controllerのバイナリーが継承されていても、以前のcontrollerイメージの表示はfalseになります。

共通ランタイムとNFの全ビルド、および一時領域でのCompose検証が成功した後に限り、基準イメージ一式を不可分に選択します。ビルド失敗時は以前の候補と稼働用設定を保持します。ただし、準備処理でカーネルモジュールを再構築する場合はサービスが中断することがあります。開発用の切り替えが未完了なら、通常の`up`で復旧するまで基準イメージの再構築を拒否します。新しいNFイメージ一覧の形式不正や欠落はエラーになり、上流イメージへ戻しません。旧候補は引き続き読めますが、新しい基準への更新には明示的なビルドが必要です。独自指定がなかった状態へのロールバックでは現在の基準イメージを選びます。MongoDBは引き続き固定済みの上流イメージを取得し、データを保持します。

これらはローカル開発候補であり、再配布承認済みイメージではありません。対応ソース・ライセンス、SBOM、脆弱性、公開の各確認はM5に残っています。共通ランタイムのアプリケーションと初回のNFビルドは分離したビルダーを使い、gtp5gカーネルモジュールのビルドは引き続きゲストのツールを使います。既存6VMのソースツリーは参照・変更しません。NFのソーススナップショット、実効module lock、ビルド記録はホストの編集用worktreeとは分離し、ゲストの非公開の初回構築ディレクトリに保存します。共通ランタイムは毎回新しい出力先で作るため、含まれるVinberoはすべて同じ最低依存版の検査を通ります。監査には独自指定で置き換えられた基準NFイメージも含めます。

## 証跡と試験の範囲

`test one-call`は、新しいRegistration/PDUログ、PFCPセッションの削除・再作成、実際のT1/T2広告、8往復のICMP応答と期待するHTTP応答を要求します。N2 SCTP、N4 PFCP、BGP UPDATEも採取し、PFCPの確立・変更・削除の要求／応答メッセージ種別が揃うことを確認します。完全なNGAP/BGP適合性デコーダーではありません。

通信試験ではICMPの識別子・シーケンス番号をN3/N6とSRv6ブリッジで照合し、GTP-UのTEIDが観測したPFCPセッションと一致することを検証します。MUP時はUPFのN3/N6両側に該当ユーザーパケットがないことを要求します。baselineでは逆にUPF両側で同じパケットを確認し、SRv6側にはないことを要求します。BPFマップは共有カーネル上の名前検索だけに頼らず、PEごとに接続されたXDPプログラムとtail-callの参照関係から特定します。キャプチャーの起動失敗、切り詰め、パケットドロップも不合格にします。

`test lease`はpassive observerを停止し、リース失効と通常UPFへのフォールバックを確認してからobserverを起動し、実UEを再接続します。新しいpassive observerは新たなPFCPシグナリングなしでは既存セッションを復元できません。

`test restart`はMUP PE（N3／Interwork側）/MUP PE（N6／Direct側）コンテナーだけを再起動し、`up`と同じPE初期設定処理を実行します。イメージ・コンテナーIDが同じで、起動時刻が変化したことを確認します。`test network`はこの2コンテナーだけを強制再作成し、コンテナーIDとネットワーク名前空間IDが実際に変わったことを要求します。いずれもSRv6 locator経路、N6の正しいVRF／tableへの所属、N6／UEのフォールバック経路を確認し、新しい1callの前に**既存PFCPセッション**でMUP通信と通常UPF経由の通信を検証します。管理された復旧手順の試験であり、任意のデーモン障害からの無操作・無停止復旧を保証するものではありません。ブリッジ、ほかのコンテナー、物理ホスト、既存6VMは再作成しません。既存のPE netplan/networkd再設定試験をコンテナーの名前空間・エンドポイント再作成へ置き換えたもので、同一の障害ではありません。

`test neighbor`はMUP PE（N6／Direct側）上のDN向け動的近隣エントリーだけを削除します。コレクターの能動probeを休止し、エントリーの欠落を確認してから、導入済みMUP PE（N6／Direct側）定期処理が30秒以内に復元することを要求します。手動pingやエントリー注入は行わず、復旧後に通信と新しい1callを検証します。静的エントリーは削除しません。復旧結果には前後の状態とパケット証跡への参照を保持し、PEの後処理に成功しても失敗した検証を成功扱いにしません。パケット証跡には初期候補だけでなく、実際に稼働している各部品のイメージIDも記録します。

`test all`はone-call＋baseline/MUP＋lease＋restart＋network＋neighborを実行します。**クリーン構築・別ホスト再現・VM再起動の受け入れは別試験です**。これらは通信を一時切断する試験で、現在はIPv4 UE 1台が対象です。

生pcap、PEごとのBPFダンプ、結果はゲストの`/opt/srv6-mup-compact/.lab/runtime/evidence/`に保存します。`./lab evidence`で、失敗した復旧検証も含めた完了結果の概要を一覧できます。失敗時のキャプチャーも診断用に保持します。新規pcapは公開承認済みの例示ではなく、ソース書き出しから除外し、アップロードしていません。単一VM版ダッシュボードの定期probeは前述のとおりパケット検証から除外します。

## クリーン再現の手順

KVMと十分なメモリー・ストレージを持つ使い捨てのUbuntu 24.04 x86-64ホストに、履歴を含まないソースを利用者所有で配置します。既存ゲストのディスク、`.lab`、開発用ツリー、ビルドキャッシュをコピーしないでください。以下ではマシン固有の上書きを継承せず、明示的に`config/compact.example.yml`を選択します。サブネットとポートの空きを確認し、既存リソースと衝突する場合は別のプロファイルを用意してください。

```bash
./lab deps
sudo ./lab deps --apply
# Reconnect so the new libvirt/kvm group membership is active.
./lab --config config/compact.example.yml doctor
./lab --config config/compact.example.yml up --build
./lab --config config/compact.example.yml test all
./lab --config config/compact.example.yml rebuild mup-dashboard
./lab --config config/compact.example.yml rollback mup-dashboard
./lab --config config/compact.example.yml down
./lab --config config/compact.example.yml up
./lab --config config/compact.example.yml test all
./lab --config config/compact.example.yml health
./lab --config config/compact.example.yml destroy
# Only on the disposable test environment, after inspecting the preview:
./lab --config config/compact.example.yml destroy --confirm srv6-mup-compact
./lab --config config/compact.example.yml up --build
./lab --config config/compact.example.yml test all
./lab --config config/compact.example.yml health
```

非公開ログ、ソース／lockのハッシュ、2回分の所有記録、ゲストのランタイム・パケット証跡、退避アーカイブを保持します。退避ディスクが変化せず残ること、2回目のVMが新しいUUIDであること、退避ディスクではなく未変更のクラウドイメージに新しいoverlayを作っていることを確認してください。checksum検証済みの配布ベースイメージは再利用できますが、1回目のゲストのソース・バイナリー・依存キャッシュを再利用した場合はクリーン再構築とはしません。この手順は準備済みホスト1台上での**ゲスト**のクリーン構築2回であり、独立したホスト導入2回、バイト単位の同一成果物、別の物理CPUの検証ではありません。

同一物理マシン上で未準備ホストを検証する場合は、nested KVM対応の新しい12 GiB／6 vCPU Ubuntu親VM内で、8 GiB／4 vCPUの単一VMラボを1台ずつ動かせます。入れ子の仮想化を使えることが前提で、ソフトウェアエミュレーションでは代用しません。親VMとホスト予備メモリーを確保してください。容量上必要なら明示的に選んだ試験ラボだけを停止し、入れ子のゲストと親を停止した後に元のラボを復元・検証します。入れ子のゲストが稼働したまま親をsuspendしないでください。この試験はARM/macOS対応を証明しません。

## 非公開のイメージ検査

```bash
./lab audit-images
./lab audit-images --scan
```

最初のコマンドは、稼働中の全20サービスと初回構築候補、存在する場合はビルダーが選択する不変のイメージIDをプレビューするだけです。2つ目は所有するVMのSSH接続経由で、重複を除いた各イメージを`docker image save`で保存します。稼働中コンテナのcommit／export、書き込みレイヤー・volumeのコピー、使用イメージの切り替え、公開は行いません。ホストのDockerデーモンは不要です。保存アーカイブとスキャナーキャッシュの空き容量を用意してください。実行前に余裕を含めた容量を確認します。

スキャン前にファイルを展開せず、アーカイブ内のmanifest・設定・各レイヤーのハッシュを検証します。従来のDocker設定IDとOCIマニフェストIDのどちらも、スキャナーが報告する設定ID・rootfsレイヤーIDへ対応付けます。OCIイメージのmanifestと設定のdigestが異なるという理由だけで誤って拒否しないようにしています。

checksum固定のTrivyをホスト上で直列実行し、内部並列数も制限して保存アーカイブを検査します。新しい脆弱性DBを1回取得し、その実行中は固定します。ツール・DBのメタデータとDBのSHA-256も記録します。対象はパッケージの脆弱性・ライセンス、ファイルシステムとイメージ設定の秘密情報パターンです。依存情報の照会はofflineモードですが、DBとスキャナーの取得にはネットワークが必要です。既存のTrivy環境変数・設定・ignoreファイルによる無断の検出抑制は許可しません。実装は[Trivy公式のimageオプション](https://trivy.dev/docs/v0.74/guide/references/configuration/cli/trivy_image/)に従います。

非公開の出力先は`.lab/<vm-name>/image-audits/<run>/`で、イメージアーカイブ、検査前後の一覧、生JSON、イメージごとのポリシー結果、CycloneDX SBOM、スキャナーログ、manifestを保存します。ディレクトリは`0700`、出力ファイルは`0600`です。秘密情報に一致した値を含む可能性があるため、公開例としてアップロードしないでください。manifestは検査完了とポリシー合格を分け、`publication_approved`は常にfalseにします。HIGH／CRITICAL、不明・未確認ライセンス、秘密情報への一致、一覧欠落、スキャナー失敗、使用イメージやDBの変化がある場合は合格にしません。非ゼロ終了でも完了分の結果と失敗箇所の診断を保持し、イメージのpruneや弱い条件での無断再試行はしません。再実行は新しい非公開の検査ディレクトリを作ります。

これはM5の証跡収集であり、配布を承認するリリース判定ではありません。ソース配布用のホストツールのライセンス例外は、コンテナイメージには適用しません。スキャナー生成のSBOMは、C/C++や埋め込みeBPFの依存を完全に検出できた証明ではありません。削除・上書き済みレイヤーとビルド履歴、パターン検出を超えるプライバシー確認、対応ソースと通知、ゲストOS／gtp5g、選択されていない上流NFイメージ、署名付き来歴、匿名取得は別途作業が必要です。ビルダーがなければ未検査として明記します。このコマンドは現在の単一VMだけを検査し、既存6VMは検査・変更しません。リポジトリのソース検査は`.lab`と`worktrees`を除外し、イメージ検査は明示的に分けて行います。

イメージのライセンス分類は現在、以下の初回記録で暫定利用したソース用許可リストではなく、専用ポリシーを使用します。既知のGPL/LGPLパッケージは対応ソース・通知の確認要件に分類し、自動承認しません。最低依存バージョンの更新、NFの明示的な`--clean-runtime`再ビルド、鍵の由来、非公開資料の収集は[イメージ配布レビュー](image-distribution.ja.md)にまとめています。

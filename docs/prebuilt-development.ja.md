# 構築済みイメージでの起動とソース改変

[English](prebuilt-development.md) | 日本語

## 同じラボで、イメージの取得方法だけを変える

通常利用と開発で、単一VM、Composeトポロジー、設定、ダッシュボード、試験を共通にします。開発用に別のネットワークは作りません。ホストの前提条件は[コンパクト構成のセットアップ](compact-lab.ja.md)を参照してください。

現在利用できるソースビルド経路で、画面に見えるダッシュボード変更とrollbackまで順に試すには、[ハンズオン](hands-on.ja.md)を参照してください。

| 目的 | イメージの取得 | ビルダー |
| --- | --- | --- |
| リリース版を起動 | 固定した共通ランタイムと11 NFを取得 | ダウンロードしない |
| 部品を改変 | 編集したソースのスナップショットから対象部品を再構築・適用 | 対応イメージを必要時だけ取得 |
| 配布イメージなしで構築 | 明示的にローカルでソースビルド | リポジトリ内のレシピから構築 |

**リリースイメージはまだ公開していません。** 同梱の`config/compact-release.json`は意図的に`release: null`です。初回の`./lab up`はVMを作る前に停止します。現時点では`./lab up --build`を使い、その後は通常の起動で既存のローカルイメージ一式を再利用してください。イメージ取得機構の実装は再配布の承認ではありません。

## 利用者の操作

**現在、ソースから単一VMラボを新規構築する場合**は、新規DB用のゲストAVX対応を含め、[単一VMセットアップ](compact-lab.ja.md)のホスト要件を確認します。まず依存導入をプレビュー・適用し、グループ所属が変わったらログアウト・再ログインしてください。

```bash
./lab deps
sudo ./lab deps --apply
```

このチェックアウトへ戻り、ラボを構築して確認します。

```bash
./lab doctor
./lab up --build
./lab health
./lab test one-call
```

既存ラボは新しい初回ビルドを行わず、元のチェックアウトとプロファイルで通常の`./lab up`を使い、既存イメージを再利用します。改変する場合は、まず対象部品のソースの場所を確認して編集します。

```bash
./lab source mup-controller
```

表示された場所のソースを編集してから実行します。

```bash
./lab rebuild mup-controller
./lab rollback mup-controller
```

ホストの前提パッケージ導入後は再ログインが必要な場合があります。`source`が表示する場所を編集してから`rebuild`してください。自作Go部品は本体ソースツリー、外部部品は保持される編集用worktreeを使います。未コミットの編集とローカルコミットも反映します。無関係な部品の改変イメージは保持します。rollbackが戻すのはイメージであり、ソースやDBの内容ではありません。起動と多くの部品の適用はUEの再接続を伴い、無停止操作ではありません。

### 将来の構築済みリリース用手順

レビュー済みイメージと、対応するnullではないリリース定義が公開された後に限り、対応するソースアーカイブ／タグと準備済みホストで実行します。

```bash
./lab release
./lab up
./lab health
```

これは現在のソースビルド手順ではありません。同梱のnull定義では、ローカルでソースビルドしたVMがあっても`./lab release`は意図的に失敗するため、現在の手順には含めません。検査を削除したり架空のリリースを設定したりしないでください。

リリースに個別審査済みビルダーがない場合、別環境を黙って構築せず、明確な案内付きで停止します。利用者はリポジトリ内のレシピによるローカル構築を選べます。

```bash
./lab rebuild mup-controller --local-builder
./lab rebuild free5gc-smf --local-builder --clean-runtime
```

ローカル候補では従来どおりローカルビルダーを自動使用します。ローカル再構築ではベース、ツールのアーカイブ、レシピを固定しますが、ディストリビューションのパッケージ配布元はスナップショット固定ではないため、ビット単位の一致は主張しません。起動制御や依存ロックのソースを変える場合は対応する新しいリリースか、明示的なローカルビルドが必要です。導入後のGoアプリケーションの編集は、対応ビルダーを無効にせず行えます。

## リリース定義と安全な失敗

`scripts/compact_release.py`がバージョン付き定義を検証します。外側のキーは`schema_version`（整数1）と`release`です。nullでないリリースは、以下の項目だけを持ちます。

| 項目 | 意味 |
| --- | --- |
| `version`, `platform` | v0.1.0などの版番号。Linux amd64のみ |
| `compatibility_sha256` | ゲスト起動制御、テンプレート、レシピ、ソース／ツールチェーン固定情報のハッシュ |
| `source_sha256` | ファイルモードを含む自作Goソーススナップショットのハッシュ |
| `runtime` | 共通イメージ。GHCRのSHA-256 digest付き`reference`と`image_id` |
| `nf_images` | 全11 NFのサービスIDごとに同じ形式のイメージ定義。DBは含めない |
| `builder` | null、または`image`定義と正確な`inputs`（レシピ、ベース、ヘッダー、ツールチェーン） |
| `database` | 既存の固定済み上流MongoDB参照。独自ミラーではない |
| `dashboard_snapshot_protocol` | 整数1 |

コミットされた定義は信頼する入力ですが、**署名ではありません**。保守者が、イメージID／digestをレビュー済みのビルド、スキャン、ライセンス証拠と対応させる必要があります。現在のソースの指紋を表示しても、イメージの構築や承認は行いません。

```bash
python3 scripts/compact_release.py --inputs
./lab release --manifest /absolute/trusted-release.json
./lab up --release /absolute/trusted-release.json
```

明示的な定義の指定は、新規プロファイルへの導入、または同じリリースの再試行に使います。異なる既存イメージ一式の置換は拒否します。リリース比較には別名のVM／プロファイルを使ってください。稼働中のベースライン更新は未実装です。拒否を回避するために所有記録やDB状態を削除してはいけません。

取得時はレジストリの正確なdigestとLinux amd64を指定し、返されたイメージIDとリポジトリdigestも照合します。12イメージ全部と一時的に生成したCompose設定の検証が成功してからベースラインを採用します。取得中断時は取得済みキャッシュを残しますが、不完全な一式は採用しません。可変タグやソースビルドへの暗黙の切り替えはありません。導入済みの一式はビルダーを取得せず再起動できます。部品／DBの復旧が未完了なら導入を止めます。MongoDBは従来の起動処理で上流から直接取得し、DBの暗黙のメジャー移行は行いません。

ゲスト準備では引き続きDockerを導入し、実行中カーネルに対して固定版gtp5gを構築します。構築済みイメージによる起動もオフラインアプライアンスではなく、GCC／build-essentialを含むカーネルビルドの前提をなくすものではありません。追加のアプリケーション用ツール（Go、CMake、Clang）は、全体を明示的にローカルビルドする場合だけ導入します。部品ビルドはDockerソケットや加入者鍵を渡さない分離した非rootビルダーで行います。

## CIと残る配布条件

通常CIは`make check`の一部として、定義・取得・失敗時の扱い・ビルダーのオフライン試験を実行します。任意のCompact image candidateワークフローは新規VMを構築し、部品の再ビルド／rollback、全パケット／復旧試験、非公開イメージ監査を実行します。公開や成果物アップロードの処理はありません。`COMPACT_CANDIDATE_CI`を`enabled`に設定し、`srv6-mup-release`ラベル付きの専用・1ジョブ限りのUbuntu/KVMランナーで、デフォルトブランチから手動実行する場合だけ動きます。事前に`compact-candidate`環境へレビュー保護を設定してください。記載済みのホスト依存、Go／Ansible試験ツール、十分なRAM／ディスク、動作するユーザーサービスセッションが必要です。信頼していないPRのコードをそのランナーで実行してはいけません。終了後も作業領域とVMディスクを非公開で保存し、後続のcheckoutや掃除で証拠・所有記録を消さないでください。成功・失敗ともゲストは停止するだけで削除しません。既存run IDの再利用は拒否します。

別のVerify published compact image identitiesワークフローはホステッドランナーで匿名取得し、ランタイムとビルダーを個別に選んで照合します。コンテナー実行やパケット疎通試験は行いません。現在のnull定義では意図的に失敗します。公開後の確認用であり、公開済みという証拠ではありません。

2026-09-24に、リポジトリのPython 270件、Goのテスト／vet、シェルとAnsibleのチェックが成功しました。同じホスト上の別VMでは、既存ローカルイメージのキャッシュを使い、起動、MUP-Cの再ビルド、実際の1call、rollback、one-call／baseline／lease／restart／network／neighborの全試験が成功しました。配布対象ソースだけのコピーもチェックと秘密情報検査に合格しました。既存の公開テスト鍵だけを厳密に指定する例外を使用しています。主ラボは再起動していません。これはローカル回帰試験であり、キャッシュなしの新規構築やレジストリのリリース試験ではありません。新しい任意CIジョブは未実行で、保護した専用ランナーの準備もpendingです。

同日の追加検証では、同じ物理ホストに別名で新規作成したVMに対し、候補構築スクリプトをローカル実行しました。そのゲストには既存のラボイメージやビルドキャッシュはありません。ソースからの起動、MUP-Cの再ビルド、1call、rollback、全パケット／復旧試験が通りました。続く監査は不変イメージ14個すべてで完了しましたが、ポリシー不合格のため候補構築コマンド全体は正しく非0で終了しました。終了処理でゲストを停止し、ディスク、ソース、非公開証跡を保持しました。主ラボは稼働を続け、最終health確認も通りました。これはGitHubランナー上のジョブでも、別物理ホスト試験でも、構築済みイメージのレジストリー取得試験でもありません。残る配布条件は後続の[イメージレビュー](image-distribution.ja.md)を参照してください。併せて追加したソース資料収集ツールは、リポジトリのPython 292件、配布対象ソースのPython 282件、Goのテスト／vet、シェル／Ansible、秘匿値を伏せるソースの秘密情報検査に合格しました。通常のGitHubワークフロー3種類も合格しています。

残る条件は[イメージ配布](image-distribution.ja.md)で管理します。現在の固定イメージの再スキャン、対応ソース／通知、ネイティブ／eBPFの網羅、秘匿情報と鍵の由来の確認、ランタイムとビルダーの個別承認、署名、明示的な公開許可です。レジストリ公開の自動化は、これらの条件とイメージパッケージの公開先が承認されるまでpendingです。ソースリポジトリは公開済みですが、レジストリーパッケージの承認ではありません。今回追加したワークフローにはパッケージ書き込み権限やレジストリ認証情報を与えていません。公開後は同じ物理ホストのイメージキャッシュが空のVMで起動し、1部品の編集・再ビルド・rollbackとパケット試験を行います。オフライン試験やキャッシュ済み環境の回帰試験は、このクリーン取得の受入試験とは区別します。

識別とデプロイ保護の仕組みは、[Dockerのdigest指定取得](https://docs.docker.com/reference/cli/docker/image/pull/)と[GitHubの環境保護](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)に基づきます。
